# Aontu after one SDK: the core is sound, the edges cost me time

*Mateen Ali, October 2026*

I didn't go looking for Aontu. I met it because the Voxgig SDK generator stores its whole model in `.aontu` files, and last week I used that generator to build an SDK for the Resend email API. By the end I had written about 350 lines of Aontu and read many more.

Aontu is a JSON superset whose single operation is unification. You make several statements about the same value, and they either narrow it to something more specific or fail. Anyone who has used CUE will recognise the idea. The basic example from the docs:

```
port: integer
port: min(1024)
port: 8080
```

```
$ aontu port.aontu
{ "port": 8080 }
```

Change the last line to `port: 80` and evaluation fails with `aontu/constraint`. Schema, constraint and data share one notation and are checked together.

## The central claim holds up

The docs promise that unification is commutative and associative, so a document has no evaluation order. I was suspicious, because the generator's own `project.aontu` starts with this comment:

```
# Included LAST by sdk.aontu, after target/target-index.aontu, because a key
# under main.kit.target.<t> can only refine a target that has already been
# defined. Declared earlier, the model build fails ...
```

So I tested it. I copied the 450 KB model from my SDK project, moved the `project.aontu` include from last to first, and evaluated both versions with aontu 0.76.0. The output was byte-for-byte identical.

The failure the comment describes does happen, but not because of order. It happens when you refine a key that is never defined anywhere:

```
main: kit: target: &: { name: key()  ext: string }
main: kit: target: ts: ext: 'ts'
main: kit: target: py: publish: version: '2.0'   # py is never added
```

```
[aontu/mapval_spread_required]: Cannot unify values at path $.main.kit.target.py.ext
The value for key ext is required (defined in spread).
```

The language behaves exactly as documented, yet a toolchain written by people close to it still has a comment that blames the wrong cause. That worries me more than any single bug. When a unification model fails, users fall back on the rule they already know, "later lines override earlier ones", and the explanation they write down becomes folklore.

## Defaults are better than CUE's

Configuration needs layering: a library sets a default, and a project changes it. Pure unification has no "later wins" rule, so Aontu adds ranked defaults. One star marks a default, and more stars make it weaker.

```
entity: &: active: **false    # library layer: weaker default
entity: card: active: *true   # project layer
```

```
{ "entity": { "card": { "active": true } } }
```

If you forget the second star, you get an error that says what went wrong and how to fix it:

```
[aontu/pref_rank_clash]: Cannot unify values at path $.entity.card.active
Two defaults of the same rank disagree. Rank one of them (`**x`) to say
which is the weaker layer, or give them the same value.
```

The same case in CUE 0.17.1:

```
x: *1 | int
x: *2 | int
```

```
x: incomplete value 1 | 2 | int
```

CUE drops both defaults and leaves you to work out why. Aontu reports which two values clashed and how to fix it. Its general error format is good too: a stable code, an explanation, and a caret under each conflicting source. `aontu explain <code>` prints the same help offline.

## Where it gets in the way

The good errors stop where the language desugars things for you. A bare default like `tier: *1` is really a disjunction underneath, and that's what leaks out when it fails:

```
tier: *1
tier: "high"
```

```
[aontu/empty]: Cannot unify values at path $.tier
Empty disjunction. The disjunction has no valid alternatives.
```

I never wrote a disjunction. The same error appears for `tier: 2.5`, because Aontu separates integers from floats (`1 & 1.0` is `nil`). For a language that sells itself as a JSON superset, that's a surprising rule. JSON has one number type, and a value like `1.0` in data generated by another tool will fail against an `integer` schema. The rule is defensible. It just needs to be on the first page, not something you find out from an error.

The second problem is churn. Recent releases renamed the file extension from `.aon` to `.aontu`, and an old include now fails like this:

```
include not readable: ./old.aon (extension: .aon)
```

The file is readable. The message has no error code and doesn't mention the rename, so a project scaffolded a month ago breaks on upgrade with no hint why. When I ran the CLI directly on my SDK model, I also got this warning three times:

```
aontu: warning: include resolved outside the entry root: .../node_modules/@voxgig/sdkgen/model/sdkgen.aontu
(a future release will deny this by default; ...)
```

Every Voxgig SDK project includes its schemas from `node_modules`, so the announced default would break all of them. The generator calls Aontu as a library, and that path doesn't show the warning, so the people affected won't see it coming. The homepage install line also pins `aontu@0.73.0`, while npm served 0.76.0 when I tested. That's three minor versions of drift on the first command a newcomer copies.

The third problem is scope. `aontu --help` lists 28 verbs, including a package manager (`add`, `publish`, `pkg vendor`), signing keys (`pkg keygen`), an MCP server, an LSP and an `AGENTS.md` generator. The core language guide is a 59-line card, which I like. But a pre-1.0 language that is still renaming its own file extension is also shipping a package registry with signatures. I'd rather see the include rules and the extension fixed, with a stability promise attached, before the language grows its own supply chain.

## Would I choose it?

Inside the Voxgig toolchain you don't get to choose, and that's fine. The model does its job, and my corrections in `guide.aontu` survived every regeneration.

As a standalone choice, I'd pick Aontu over CUE in two cases. One is when the team works in TypeScript, because Aontu has an npm implementation alongside the Go one, both checked against the same test suite. The other is when the configuration has several layers that need ranked defaults. For anything else I'd still choose CUE today, because I want the file that defines my system to depend on a smaller tool that changes slowly.

If the maintainers asked me for one change, it would be this: put an error code and a migration hint on every refusal that comes from tooling rather than unification, starting with "include not readable". The core already deserves people's trust. The edges are where newcomers lose an afternoon.
